# 指摘分類の代表ケース

## 目的

`rules/automation-operation.md`および`rules/worker-evidence.md`の`品質修正`、`接続同期差分`、`工程境界不備`を、同じ事実に対して同じ処理へ結び付ける。本文は個別taskの実績台帳ではなく、完全一致する事実へ即時適用する共通判断規則である。

## 適用手順

1. 指摘の対象、観測事実、根拠、工程影響を記録する。
2. 本文の代表ケースと事実・根拠・影響が完全一致する場合は、その分類と固定処理を適用する。
3. 複数ケースに一致する、必要な事実が不足する、または既存正本と矛盾する場合は、品質修正として進めず`工程境界不備`として`blocked`にする。
4. 新たな代表ケースは、Ownerが再発防止の有用性を判断した場合だけ、原因・適用条件・固定処理・禁止処理を一般化して追記する。過去task、固有ID、実行環境の実体値を共通ケースへ固定しない。

本書は`rules/automation-operation.md`と`rules/worker-evidence.md`の分類定義を置き換えない。定義とケースが矛盾する場合は、定義を優先して停止する。

## 品質修正

| 完全一致する事実 | 固定処理 | 禁止処理 |
| --- | --- | --- |
| 承認済み計画の成果物が明示された受入基準を満たさない | 指摘を総合報告へ集約し、承認済み範囲と予算内でImplementer→Reviewerの修正ラウンドへ進む | 接続・正本・eventの不備を同じ指摘へ混在させる |
| 成果物に対する検証結果が、承認済みの期待値と不一致である | 根拠と期待値を記録し、同一フィンガープリントの指摘を統合して修正ラウンドへ進む | attempt番号や時刻だけを新規原因として再接続する |
| 承認済み範囲の成果物または必須検証が欠落している | 成果物の担当責務へ修正要求を集約し、再確認条件を定める | 結果資料・承認・工程境界の欠落を成果物欠落と推測する |

## 接続同期差分

| 完全一致する事実 | 固定処理 | 禁止処理 |
| --- | --- | --- |
| 選択バックエンドの接続・close結果とWorker Registryの実行単位IDまたは状態だけが不一致であり、task ID、担当責務、担当resultの正本パス、内容フィンガープリントが一致する | 接続・close結果を接続・終了状態の正本としてRegistryとtask-logへ一度だけ同期し、同じ工程境界の入力ゲートを再照合する | 担当resultの内容・判定の変更、Implementerへの修正要求、Reviewer再接続、修正ラウンド、予算消費 |
| 結果資料は存在し内容も一致するが、task-logへの接続結果記録だけが欠落または古い | 接続結果をtask-logへ一度だけ同期し、重複がないことを確認する | 新規worker作成、event再発行、成果物の再実装 |
| 同一eventの接続結果が既に確定しており、別資料だけが未同期である | 確定済みeventを再利用し、未同期資料だけを同期する | `completed`または`blocked`のeventを巻き戻す |

## 工程境界不備

| 完全一致する事実 | 固定処理 | 禁止処理 |
| --- | --- | --- |
| 担当resultの正本パス、内容フィンガープリント、結果資料、承認記録、対象境界、親Coordinator、実行ディレクトリのいずれかが欠落または既知の不一致である | 当該handoff eventを`blocked`にし、原因、期待値、実際値、根拠、影響、再開条件を集約する | 接続同期差分または品質修正として継続する、ImplementerまたはReviewerを再接続する |
| 同一工程境界に異なる結果フィンガープリントのeventが並存する | 後発eventを`blocked`にし、両方のeventと根拠をOwnerへ提示する | 自動選別、取消、上書き、並行接続 |
| `review.md`が受入または条件付き受入であるにもかかわらず、OwnerのDocumenter開始承認が記録されていない | `Reviewer受入・Documenter開始承認待ち`として停止する | Documenter接続、受入を根拠とした完了・履歴操作 |
| 指摘が複数分類に一致する、または分類に必要な根拠を取得できない | `工程境界不備`として停止し、不足事実と再開条件を記録する | 安全側を理由に品質修正へ流用する |

## 維持管理

- ReviewerまたはCoordinatorは、既存ケースへ完全一致しない指摘を検出した場合、既存3分類と停止条件で処理する。代表ケースの追加自体を現行taskの完了条件にしない。
- ケース追加時は`rules/rule-dependency-map.md`に従い、分類定義、修正ラウンド、event契約、整合性チェックの参照先を同時に確認する。
- ケースの追加・変更では、同じ事実が複数分類へ入らないこと、固定処理が再接続・再試行・状態巻戻しを生まないことを`rules/idempotency.md`に従って確認する。
