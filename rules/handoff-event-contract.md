# handoff event 契約

## 目的

通常工程の引継ぎを定期監視から独立させ、結果資料の確定から次工程開始までを再実行安全に記録する。実行バックエンドはこの契約の意味を満たす通知・記録方法を選べるが、固有IDやAPI値を必須化してはならない。

## 台帳と記録責任

現行taskの通常経路の正本は`threads/<thread-name>/result/handoff-events.md`とする。完了したworker実行単位は結果資料を確定し、Workflow Coordinatorは証跡照合後にイベントを台帳へ記録・処理する。復旧監査の起動機構はこの台帳を読み取るだけで、通常経路の台帳を兼用しない。

## 必須項目

| 項目 | 意味 |
| --- | --- |
| event ID | task-id、発生元責務、工程、結果資料、内容フィンガープリントから決まる再実行安全なID。日時だけを使わない |
| task ID / 工程 | 対象taskと完了または停止した工程 |
| 発生元 | 論理責務と、取得できる場合だけ実行単位ID |
| 結果資料・フィンガープリント | 正本パスと内容同一性を確認する根拠 |
| 判定・次の処理 | 次工程開始、Owner判断要求、または停止のいずれか |
| 状態 | `queued`、`processing`、`completed`、`blocked`、`cancelled` のいずれか |
| claim | 処理責任者、claim時刻、処理Attempt番号 |
| 処理証跡 | 接続・resume・Owner提示など、実際に行った処理の根拠 |
| 再開条件 | `blocked`または未完了時に必要な判断・証跡・操作 |

## 状態遷移と確定点

```text
queued → processing → completed
   │          │
   ├──────→ cancelled
   └──────→ blocked ←─────┘
                 │
Ownerが再開を承認 → queued
```

- Coordinatorだけが`queued`を`processing`としてclaimし、同一eventを並行処理しない。
- 次工程の接続またはOwner提示の結果を台帳へ記録できた時だけ`completed`にする。接続後の記録前に中断した場合は、接続結果を先に照合し、実施済みなら`completed`、判定不能なら`blocked`にする。推測で再接続しない。
- 結果資料欠落、承認不足、対象境界不一致、既知の矛盾、または復旧不能は`blocked`とし、Owner判断なしに`queued`へ戻さない。
- `cancelled`はOwnerが当該taskまたは工程を明示的に中止した場合だけ使用する。過去eventを削除・上書きしない。

## ACE-001：単一工程eventの重複検出

標準工程は同時に一つの実行単位だけを稼働させる。Coordinatorは待機eventを恣意的に統合・選別せず、同一工程境界の重複または矛盾を検出する。

- 同一event IDは同一の結果を表す。既存eventの状態を参照し、結果資料・通知・次工程接続を重複して行わない。
- 同一task、同一発生元責務、同一次工程で、異なる結果フィンガープリントのeventが`queued`または`processing`にある場合は、どちらも自動選別・取消・上書きをしない。後発eventを`blocked`とし、両event ID、結果資料、フィンガープリント、検出時点、再開条件を記録してOwnerへ提示する。
- `completed`または`blocked`のeventは後発eventによって状態を変更しない。工程をやり直すにはOwnerが再開条件と正本結果を明示する。
- 通知本文、時刻、実行単位IDだけで新旧や優先順位を決めない。

## 発行・受領の順序

1. worker実行単位が担当結果資料と完了報告を確定する。
2. Coordinatorが入力ゲート、結果資料、承認、実行環境境界を照合する。
3. Coordinatorが`queued` eventを追記し、同一eventの既存状態を確認する。
4. Coordinatorが同一工程境界のevent IDと結果フィンガープリントを照合し、重複なら既存eventを再利用し、矛盾なら`blocked`としてから処理対象をclaimする。
5. Coordinatorがclaimを記録してから、承認済みの次工程を接続・resumeする、またはOwner判断を提示する。
6. 接続結果または提示結果を記録し、状態を`completed`または`blocked`へ確定する。

通知機構が一時的に利用不能でも、結果資料と台帳を直接照合できる限り通常工程を停止しない。Coordinatorの次回実行または復旧監査は未処理eventを照合して再開できる。ただし、通知不能を理由にeventを新規作成・置換してはならない。

## 無進捗の監査と復旧

長時間の作業であること自体は停止理由にしない。Coordinatorは、選択したバックエンド規約と`current-task.md`の進捗監査方針に従い、`processing` eventごとに結果資料の内容フィンガープリント、Worker Registryの状態・確認証跡、eventのclaim・処理証跡を進捗根拠として照合する。

- 直前の監査から有効な進捗根拠が増えている場合は、作業継続として記録し、復旧・再接続・Owner判断を行わない。
- 連続する監査で同じeventと同じ原因の無進捗が確認された場合は、進捗監査方針の基準に従い復旧を一度だけ試み、その対象、比較した根拠、結果を記録する。同じ根拠のまま並行または反復して再接続しない。
- 方針上の上限に達した無進捗、または復旧後も同じ無進捗が続く場合は、eventを`blocked`へ確定し、原因、影響、比較した証跡、実施済み復旧、再開条件を集約してOwnerへ提示する。後続eventは進めない。
- API観測値の未取得だけは無進捗とみなさない。代替証跡に矛盾がなければ`未確認`として記録し、通常経路を継続する。

進捗監査の回数・状態値・起動機構はバックエンド固有であり、共通契約に固定しない。監査のたびに、対象event、比較した前後の証跡、判定、次の許容操作を台帳または担当resultへ記録する。

## 実行基盤の境界

本契約は常駐ディスパッチャーの新規実装を要求しない。通常経路は選択したAI実行バックエンド内で、Coordinatorがworker完了を待機し、受領したeventを同じCoordinator実行で処理する。AIツール外のサービス、独自の実行プロセス、特定言語のランタイムを、自律サイクルの前提にしてはならない。バックエンドが完了待機または通知を提供しない場合は、そのバックエンドでは自律サイクルを有効化しない。

## 受入条件

- `current-task.md`に台帳パス、通知方式、Coordinator、復旧監査方式が記録されている
- `current-task.md`に進捗監査方針と修正・再レビュー予算の解決根拠が記録されている
- 各eventが必須項目と状態遷移に従い、同じeventの重複接続を防げる
- 同一event IDは二重接続されず、同一工程・異なる結果フィンガープリントは自動選別せず`blocked`になる
- 通常経路はevent発行・claim後に開始し、復旧監査の実行待ちを含まない
- 復旧監査は未処理・残留eventの照合だけを行い、状態変更はCoordinatorの通常手順に委ねる
