# Worker入力・証跡・再確認ルール

## 次工程へ接続する前の入力ゲート

各 worker は作業開始前に次を確認する。不足、矛盾、古い情報がある場合は作業を開始せず「評価中」として親タスクへ報告する。

- `docs/current-task.md` が最新である
- 対象リポジトリ、対象ブランチ、作業領域が一致している
- 前工程の結果ファイルが存在する
- 承認が必要な工程ではOwnerの承認が記録されている
- 最新の一次資料、課題管理、変更管理、レビューコメントを確認できる
- 未確認事項、保留事項、前回指摘が確認できる

## 証跡の記録

結果ファイルには、少なくとも次を記録する。

- 事実：実際に確認できた内容
- 根拠：ファイル、ログ、コマンド、画面、レビュー結果など
- 未確認：確認できなかった内容と理由
- 推測：事実と分離した推定
- 判定：定義済みの判定値

「確認済み」と記録する場合は、必ず根拠を併記する。実環境、外部サービス、利用者向け表示を確認できない場合は、未確認または条件付きとして記録する。

## 修正サイクル

Reviewerの指摘ごとに、次の状態を記録する。

```text
指摘ID：
指摘内容：
対応対象：
Implementer修正：
Tester再検証：
Security Operator再確認：対象 / 対象外 / 未実施
Reviewer再判定：
```

認証、権限、外部連携、ログ、状態遷移、リトライ、データ保護に関わる修正は、Security Operatorの再確認を完了するまでDocumenterへ接続しない。

## データ・外部連携・再実行

- 検証データは合成データを優先し、適用範囲、既存データへの影響、復元方法を記録する
- 再実行、重複、部分成功、タイムアウト、成功済み処理の再受信を確認する
- 複数の外部連携経路は、責務、対象識別子、送信項目、外部応答、状態更新を対応付ける
- 外部入力やURLをエラー・ログへそのまま出力せず、安全なエラー種別と最小限の診断情報へ変換する
- 処理状態、外部応答、状態更新、利用者向け結果、監視結果を別々に判定する
- 一時的な設定変更を行う場合は、変更前の参照先、成果物識別子、自動化条件、復元結果を記録する

## 仕様書・rulesの適用範囲

- 正となる仕様書を特定し、見出し、用語、構成、記載粒度を確認する
- rulesは適用範囲、期間、状態、更新条件、採用理由を記録する
- 既存の粒度を超える内部実装や、別資料との重複記載を追加しない
