# Worker入力・証跡・再確認ルール

## 次工程へ接続する前の入力ゲート

各 worker は作業開始前に次を確認する。不足、矛盾、古い情報がある場合は作業を開始せず「評価中」として親タスクへ報告する。

- 対象スレッドの `threads/<thread-name>/docs/current-task.md` が最新である
- `current-task.md` に記載されたスレッド名が、workerに割り当てられたスレッドと一致している
- 対象リポジトリへアクセスでき、対象ブランチとタスク対象が一致している
- 自身のCodexプロジェクトIDが `current-task.md` の期待プロジェクトIDと一致している
- 自身のCodex実行ディレクトリを確認し、`current-task.md` に記録する
- CodexプロジェクトID、Codex実行ディレクトリ、対象リポジトリを確認できない場合は作業を開始しない
- 対象スレッドとCodexプロジェクトが1対1で対応している
- 前工程の結果ファイルが存在する
- 承認が必要な工程ではOwnerの承認が記録されている
- 最新の一次資料、課題管理、変更管理、レビューコメントを確認できる
- 未確認事項、保留事項、前回指摘が確認できる

## 証跡の記録

結果ファイルには、少なくとも次を記録する。

- 事実：実際に確認できた内容
- 根拠：ファイル、ログ、コマンド、画面、レビュー結果など
- 未確認：確認できなかった内容と理由
- 推測：事実と分離した推定
- 判定：定義済みの判定値
- ログトレーサビリティ：秘密情報・個人情報を含めず、処理の進捗、対象データ、最終的な状態、発生事象を的確なメッセージ（例外発生時のエラーメッセージを含む）で追跡できること

「確認済み」と記録する場合は、必ず根拠を併記する。実環境、外部サービス、利用者向け表示を確認できない場合は、未確認または条件付きとして記録する。

### プロジェクト所属・作業環境の確認

各workerは作業開始前に、自身のCodexプロジェクトID、Codex実行ディレクトリ、対象リポジトリへのアクセス可否を確認する。対象スレッドとプロジェクトの対応が1対1でない場合、projectIdが一致しない場合、対象リポジトリへアクセスできない場合、またはスレッド名、リポジトリ、ブランチのいずれかが一致しない場合、作業を開始せず親タスクへ実際の値と期待値を報告する。Codex実行ディレクトリは対象リポジトリと一致しなくてもよい。workerが既存チャットを別プロジェクトへ自動的に再紐付けすることは前提にせず、Ownerによる修正または正しいプロジェクトでの再作成を待機する。

`current-task.md` には、次の6項目を記載する。

```markdown
- スレッド名：
- CodexプロジェクトID：
- Codex実行ディレクトリ：
- 対象リポジトリ：
- ベースブランチ：
- 作業ブランチ：
```

Codex実行ディレクトリと対象リポジトリは別項目として扱う。Codex実行ディレクトリは実際のworker環境、対象リポジトリはタスクで操作するリポジトリの絶対パスを記録する。確認結果は担当の結果ファイルに記録する。

Implementer以降のworkerは、完了条件の確認時にログトレーサビリティを確認する。確認できない場合は未確認事項とOwner判断へ記録し、確認なしに完了扱いとしない。秘密情報・個人情報はログへ出力せず、処理の進捗、対象データ、最終的な状態、何が発生したかが分かる的確なメッセージ（例外発生時のエラーメッセージを含む）と、安全な識別子で追跡できることを確認する。

### ログトレーサビリティ確認項目

Implementer以降のworkerは、該当しない項目を `対象外` と明記したうえで、次のチェック結果を担当の結果ファイルへ記録する。

| 確認項目 | 確認結果 | 根拠・未確認理由 |
| --- | --- | --- |
| 処理識別子で一連の処理を追跡できる | 確認済み / 未確認 / 対象外 |  |
| 処理開始を確認できる | 確認済み / 未確認 / 対象外 |  |
| 主要な状態遷移を確認できる | 確認済み / 未確認 / 対象外 |  |
| 外部呼び出しと応答を対応付けられる | 確認済み / 未確認 / 対象外 |  |
| 正常終了または失敗を確認できる | 確認済み / 未確認 / 対象外 |  |
| 例外種別と原因調査に必要な情報を確認できる | 確認済み / 未確認 / 対象外 |  |
| 再試行・重複処理を追跡できる | 確認済み / 未確認 / 対象外 |  |
| 秘密情報・個人情報・過剰な外部入力が出力されていない | 確認済み / 未確認 / 対象外 |  |

### アプリケーションログの確認結果

ログトレーサビリティの確認対象は、対象プロジェクトのアプリケーションログ、監視ログ、分散トレースなどの実行時記録とする。worker間の引き継ぎに使用する `threads/<thread-name>/result/*.md` は、ログトレーサビリティの確認根拠そのものとはしない。

- `確認済み`：対象アプリケーションの実行時記録を実測し、必要な情報と根拠を確認できた
- `未確認`：ログがない、必要な情報が不足している、または実行環境へアクセスできないため確認できない
- `対象外`：対象処理に実行時ログが不要であることをPlannerが理由付きで計画へ記載し、Ownerが承認している
- ログが存在しないことだけを理由に `対象外` としてはならない。理由が未承認の場合は `未確認` とする
- `未確認` の場合は、未確認理由、不足項目、影響、推奨対応をOwner判断へ記録する

## Owner判断

すべてのworkerは、最終応答と担当の結果ファイルに `Owner判断` と `Owner判断 (追記)` の2セクションをMarkdownテーブルで記載する。Documenterの担当結果ファイルは `threads/<thread-name>/result/task-log.md` とする。判断が必要な事項は、少なくとも次の項目を記録する。

| 記録日時 | 確認事項 | 推奨対応 | 未対応での影響 | Owner判断状態 | 根拠 |
| --- | --- | --- | --- | --- | --- |
| YYYY-MM-DD | <判断が必要な確認事項> | <推奨する対応> | <対応しない場合の影響> | 要判断 | <結果ファイル・ログなど> |

### Owner判断 (追記)

| 記録日時 | 確認事項 | 推奨対応 | 未対応での影響 | Owner判断状態 | 根拠 |
| --- | --- | --- | --- | --- | --- |
| YYYY-MM-DD | <今回の報告・再検証で発生または変化した事項。なければ「なし」> | <推奨する対応。なければ「なし」> | <未対応での影響。なければ「なし」> | 要判断 / なし | <結果ファイル・ログなど。なければ「なし」> |

- `Owner判断` には、その時点で有効な判断事項を集約して記載する
- `Owner判断 (追記)` には、今回の報告・再検証で新たに発生または変化した判断事項だけを記載する
- 初回報告で指摘がない場合は、`Owner判断` に全項目を `なし` とした1行だけを記載し、`Owner判断 (追記)` は作成しない
- 同様の内容を追記する場合は、古い追記を残して行数を増やさず、最新の内容へ移動・更新する
- 再検証で追記した判断事項が次の報告でも有効な場合は、内容を `Owner判断` へ統合し、`Owner判断 (追記)` には新しい差分だけを記載する
- 最終報告では、これまでの判断事項を `Owner判断` へ統合し、`Owner判断 (追記)` は全項目を `なし` とした1行で終える
- 判断事項が残ったままの場合は `なし` で終わらせず、親タスクへOwner判断を求めてDocumenterまたは次工程へ接続しない

## 修正サイクル

Reviewerの指摘ごとに、次の状態を記録する。

```text
指摘ID：
指摘内容：
対応対象：
Implementer修正：
Tester再検証：
Security Operator再確認：対象 / 対象外 / 未実施
Reviewer再判定：
```

認証、権限、外部連携、ログ、状態遷移、リトライ、データ保護に関わる修正は、Security Operatorの再確認を完了するまでDocumenterへ接続しない。

## データ・外部連携・再実行

- 検証データは合成データを優先し、適用範囲、既存データへの影響、復元方法を記録する
- 再実行、重複、部分成功、タイムアウト、成功済み処理の再受信を確認する
- 複数の外部連携経路は、責務、対象識別子、送信項目、外部応答、状態更新を対応付ける
- 外部入力やURLをエラー・ログへそのまま出力せず、安全なエラー種別と最小限の診断情報へ変換する
- 処理状態、外部応答、状態更新、利用者向け結果、監視結果を別々に判定する
- 一時的な設定変更を行う場合は、変更前の参照先、成果物識別子、自動化条件、復元結果を記録する

## 仕様書・rulesの適用範囲

- 正となる仕様書を特定し、見出し、用語、構成、記載粒度を確認する
- rulesは適用範囲、期間、状態、更新条件、採用理由を記録する
- 既存の粒度を超える内部実装や、別資料との重複記載を追加しない
