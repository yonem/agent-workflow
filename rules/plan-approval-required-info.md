# 計画関連Owner向け回答の必須情報

承認ゲートの読み取り専用判定、共通出力、人の判断境界は`rules/read-only-automation-gates.md`を正本とする。本書は計画承認で確認する必須情報と資料形式を定義し、承認そのものを自動化しない。

計画に関するOwner向け回答で、承認対象と実行環境を取り違えないための必須記録を定義する。実行バックエンド固有の指定制約は対象taskの実行バックエンド設定を正本とし、本ルールやOwner回答へ重複記載しない。

## 適用範囲

次の計画関連回答すべてに適用する。

- 計画作成完了、承認待ち、承認、否認、保留
- 再承認、計画変更、再開、中断、Ownerへの計画状況報告

## 必須情報

対象範囲の回答本文または承認記録には、毎回次を含める。

| 項目 | 記録内容 |
| --- | --- |
| 対象リポジトリ | 操作対象の絶対パス。`current-task.md`と一致すること |
| 実行ディレクトリ | workerが実行する絶対パス。`current-task.md`と一致すること |
| ベースブランチ | 計画の基準となるブランチ |
| 作業ブランチ | 使用するブランチ名、または新規作成の明示 |

タスクID、対象スレッド、実行コンテキスト、計画ファイルは、`current-task.md`と`plan.md`から一意に特定できる状態にする。実行バックエンドは明示指定または適用中ローカルルールから解決し、同じ選択を計画承認資料へ重複記載しない。解決根拠の変更、競合、または未解決の場合だけ計画資料へ明示し、承認を求める。Owner判断を含む場合は、`rules/worker-evidence.md`の判断ID・要約・Owner回答の形式を使用し、Owner回答ブロックにはOJ行だけを記載する。必須4項目はOwner回答ブロックとは別の、一つの計画必須情報ブロックへ4行で記載する。必須4項目を個別のコードブロックへ分割しない。

task-idの採番根拠は、実際に作成・確定された論理タスク台帳とし、候補資料の識別子、ファイル名、日時だけを根拠にしない。台帳上の欠落・誤採番・重複・未確定がある場合は、計画承認・task-id変更・後工程接続を停止する。タスク切替時は、旧資料の退避、manifest、index行、task-progressの切替完了を確認するまで新task-idを現行正本として確定しない。

## 計画承認資料の固定テンプレート

計画承認を求める場合は、imの要件定義をそのまま再掲せず、人間が承認可否を判断するための計画承認資料を、次の順序・見出しで作成する。見出しの省略、順序変更、関連情報の別章への分散、表の列変更をしてはならない。該当しない項目は「該当なし」と理由を記載する。

### 1. 基本情報

次の5項目を同じ章に記載する。作業ブランチは計画承認前に実作成せず、作成するブランチ案を記載する。task-id未採番の場合は「未採番（計画承認後に採番）」と記載し、推測で補完しない。

| 項目 | 記載内容 |
| --- | --- |
| 作業ディレクトリ | 対象作業ディレクトリの実測値 |
| 対象リポジトリ | 対象リポジトリの実測値 |
| ベースブランチ | 計画の基準ブランチ |
| 作業ブランチ案 | 承認後に作成するブランチ案。実作成済みと混同しない |
| タスクID | 論理タスク台帳の確定値、または未採番の明示 |

### 2. 目的・期待効果

変更の目的、解決する問題、期待する効果を記載する。目的と変更内容を同じ文に埋没させず、承認対象の判断理由を先に示す。

### 3. 目的達成に必要な修正内容の要約

目的ごとに必要な修正を短文で整理する。要約には一意の修正IDを付け、目的との対応を追跡可能にする。

| 修正ID | 目的 | 必要な修正 |
| --- | --- | --- |
| CHG-xxx | <対応する目的> | <目的達成に必要な修正の要約> |

`CHG-xxx`は資料内で一意なプレースホルダー形式とし、実際の計画では対象資料内で重複しない識別子へ置換する。

### 4. 変更箇所の詳細

修正要約ごとに、実装・資料更新・運用変更の処理単位へ細分化して記載する。各処理単位に必要な情報をまとめ、別章へ参照を分散させない。

| 修正ID | 処理単位 | 変更対象 | 現状の処理 | 変更後の処理 | 責任・証跡 | 検証方法 | 影響 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| CHG-xxx | <処理単位> | <資料・ルール・処理> | <現状> | <変更後> | <責任者・記録先> | <確認方法> | <影響範囲> |

修正要約から処理単位へ漏れなく追跡できること、現状と変更後を混同しないこと、処理単位を過大な一括表現で済ませないことを必須とする。

### 5. 対象外・変更しない範囲

今回実施しない対象、既存のまま維持する処理、後続タスク候補を同じ章へ集約する。

### 6. 完了判定

計画承認判断に必要な項目をチェックボックスで記載する。

```text
[ ] 基本情報5項目が揃い、正本と一致している
[ ] 作業ブランチ案と実ブランチ作成前の状態が明確である
[ ] task-idの採番状態と採番根拠が明確である
[ ] 目的・期待効果が明確である
[ ] 目的と修正内容の要約が対応している
[ ] 修正内容の要約から処理単位別の変更詳細へ追跡できる
[ ] 各処理単位に現状・変更後・対象・責任・証跡・検証・影響がある
[ ] 対象外・変更しない範囲が明確である
[ ] 完了条件・受入条件・検証方法が明確である
[ ] リスク・停止条件・復旧・再開条件が明確である
[ ] 移行方法と既存運用への影響が明確である
[ ] 承認前に実施しない操作と承認後に実施する操作が明確である
```

### 7. リスク・停止・移行・承認対象

リスク、停止条件、復旧・再開条件、移行方法、既存運用への影響、承認対象の要約を関連項目ごとに集約する。完了判定の補足を別の場所へ点在させない。

## テンプレート適用時の停止条件

上記の見出し、固定表、必須チェック項目のいずれかが欠落、順序違反、列変更、未確認、正本不一致の場合、計画承認を求めず、Planner接続・task-id確定・作業ブランチ作成・後工程接続を停止する。修正後に資料全体を再照合する。

計画承認判断資料の正本は現行スレッドの`threads/<thread-name>/docs/plan-proposal.md`とする。`threads/<thread-name>/result/plan.md`はAgent間の連絡・引き継ぎ用資料であり、機械的な情報の蓄積を許容するが、人間向け承認資料の代替にしない。両資料の対象・対象外・完了条件・基本情報に不一致がある場合は、承認や後工程接続を停止する。`current-task.md`は識別情報、`task-progress.md`は共通進捗の正本であり、計画の代替にしない。

`docs/plan-proposal.md`と`result/plan.md`はPlannerが同じ計画作成工程で作成する。Planner接続前にこれらの資料の存在や妥当性を確認条件にしてはならない。Plannerの作成後に、`docs/plan-proposal.md`の固定テンプレート、両資料の重要項目一致、計画の承認判断可能性を確認し、欠落・不一致があれば計画承認要求、task-id確定、作業ブランチ確定、後工程接続を停止する。

## 計画資料の責務分離

| 資料 | 利用者 | 目的 | 記載方針 |
| --- | --- | --- | --- |
| `docs/plan-proposal.md` | 人間、Owner | 計画承認の判断 | 可読性重視。固定テンプレート、目的、修正要約、処理単位別詳細、完了判定、リスク、移行、承認対象を記載 |
| `result/plan.md` | Planner、Implementer、Reviewer、Documenter | Agent間の連絡・引き継ぎ | 機械的な識別情報、状態、照合値、入力・出力、未確認事項、接続条件を記載してよい |

`docs/plan-proposal.md`は`result/plan.md`の単純な全文複製にせず、人間の承認判断に必要な関連情報を集約する。`result/plan.md`だけが存在する、`docs/plan-proposal.md`が欠落する、または両資料の重要項目が不一致の場合は、計画承認を要求せず停止する。

計画関連回答には、計画状態を `作成済み`、`Owner返却済み`、`Owner承認済み`、`Implementer接続可` のいずれかで明記する。計画状態は段階を飛ばして更新せず、`報告済み`だけを承認済みの根拠にしない。

## Owner判断本文の表示（OJ行のみ）

Owner判断を含む計画関連回答では、表への記録だけでなく、`rules/worker-evidence.md`の規定に従い、判断ごとの回答を一つのコピー可能なブロックコードで本文へ表示する。Owner回答ブロックにはOJ行だけを含める。規定値は`=yes`とし、変更が必要な判断だけ回答値を変更する。

IDなし、要約なし、不明なID、重複ID、対象外IDは自動適用しない。判断の意味・採番・継続は `rules/worker-evidence.md`、報告書内の配置は `rules/worker-report-template.md`を正本とする。

## OJ回答送信直前の必須チェック

Owner判断を求める回答を送信する直前に、回答者は次のチェックを実施する。チェック結果を確認できない場合、OJ回答を送信せず停止する。

```text
[ ] Owner判断が必要な未回答・保留・不明・新規の論点だけを抽出した
[ ] 各論点に一意のOJ-IDと要約がある
[ ] 各OJ-IDの要約と推奨対応が対応している
[ ] 回答値の規定値を=yesとした
[ ] OJ回答ブロックが1つのコードブロックにまとまっている
[ ] OJ回答ブロックにはOJ行だけを記載した
[ ] 必須4項目が必要な回答では、OJ回答ブロックと別の1つの4行ブロックに分離した
[ ] 回答済みのOJ-IDを再掲していない
[ ] OJ-IDの重複、欠落、不明、対象外がない
```

1項目でも未確認、形式違反、要約不一致、重複、回答済み判断の再掲がある場合は送信せず、欠落項目・期待値・実際値・停止理由を`result/`へ記録する。モデルの推論レベルや回答の簡潔さを理由にこのチェックを省略してはならない。

## 計画必須情報ブロック

Owner回答ブロックとは別に、計画関連回答へ次の4項目を一つのコードブロックへ4行で記載する。見出しや説明を各行の間に挿入せず、4項目を個別のコードブロックへ分割しない。

```text
対象リポジトリ: <絶対パス>
実行ディレクトリ: <絶対パス>
ベースブランチ: <branch>
作業ブランチ: <branch>
```

## 回答送信直前の必須チェック

計画関連の回答をOwnerへ送信する直前に、回答者は次のチェックを実施する。チェック結果を確認できない場合、回答を送信せず停止する。

```text
[ ] 計画関連回答であることを判定した
[ ] 必須4項目がすべて存在する
[ ] 必須4項目が1つのコードブロックにまとまっている
[ ] 必須4項目が説明文を挟まない4行である
[ ] Owner判断ブロックと必須情報ブロックを分離した
[ ] 対象リポジトリ、実行ディレクトリ、ベースブランチ、作業ブランチが正本と一致する
[ ] Owner判断の回答済み項目を再掲していない
[ ] 未回答・保留・不明・新規の判断だけを回答プロンプトへ含めた
```

1項目でも未確認、空欄、形式違反、正本不一致がある場合は、回答を送信せず、欠落項目・期待値・実際値・停止理由を`result/`へ記録する。モデルの推論レベルや回答の簡潔さを理由にこのチェックを省略してはならない。

- Plannerまたは親タスクは、4つの必須情報が欠落、空欄、期待値不一致、または解釈不能の場合、承認済みとして後工程へ接続せずOwnerへ確認を求める。
- Ownerの回答がIDなし、対象ID不明、重複、対象外、または必須情報との対応不明の場合は、自動補完・自動適用せず、計画承認を保留する。
- Ownerの回答として受理できるのは、Ownerチャットから対象判断ID・要約・回答が明示された回答だけとする。Planner、Implementer、親タスク、別workerの伝聞や解釈はOwner回答として自動適用しない。
- Owner判断が1件でも`要判断`、`未回答`、`保留`、不明、対応不明のまま残る場合は、計画承認を完了扱いにせず、後工程へ接続しない。残件ごとのID・要約・推奨回答プロンプトを提示し、全件の明示回答を受領する。
- 回答済みのOwner判断は、後続の回答プロンプトへ再掲しない。回答プロンプトには未回答・保留・不明な判断と、今回新たに発生した増分判断だけを含める。
- タスク切替時は、既承認・継承可能、範囲変更による再判断、未回答、新規を分類する。既承認・継承可能な判断は再掲せず、同一論点の再判断は既存OJ-IDを継続し、別論点だけ新しいOJ-IDを採番する。
- 計画変更により回答済み判断の再承認が必要になった場合だけ、再判断の理由を記録して残件へ戻し、同一論理判断は既存OJ-IDを継続する。別論点は新しいOJ-IDを採番する。
- 残件がない場合は、計画関連回答に`Owner判断残件：なし`、`回答プロンプト：なし`を付記する。
- 指定モデル・推論レベルは、Workerタスク設定の正本を参照して照合し、計画承認の回答へ固定値を複製しない。
- 承認後に対象リポジトリ、実行ディレクトリ、ブランチ、実行コンテキスト、スレッドが変わった場合は、変更後の必須情報を再提示し、Ownerの再承認を得る。
- 承認後に対象、対象外、完了条件、識別情報、履歴方針、実行環境のいずれかが変わった場合は、変更前後の差分を提示して計画を再承認待ちへ戻す。変更後の計画を承認済みとして引き継がない。
- Plannerへの追加ヒアリングは計画の事実確認に限り、ヒアリング結果だけで計画変更や後工程接続を確定しない。

## 記録

Plannerまたは計画状況を報告するworkerは、`plan.md`のOwner判断へ、必須情報、Owner回答、判断ID、承認日時、根拠を記録する。また、Ownerへの返却先、Owner回答の記録元、計画状態、変更前後の差分を記録する。後工程は、承認記録と`current-task.md`の値が一致することを入力ゲートで確認し、不一致時は作業を開始しない。
