# 実行環境の移植性とイベント駆動の共通ルール

## 目的

共通ワークフローは特定のAI製品、会話機構、API、監視方式に依存させない。役割、能力、入出力、状態、判定基準、証跡、停止条件を共通仕様とし、実行環境固有の操作は実行バックエンドへ分離する。

## 共通概念

- **Workflow Coordinator**：承認済み計画に従い、handoff eventを照合して次工程を開始、停止、またはOwner判断要求へ分岐する役割。
- **実行バックエンド**：worker接続、再開、完了通知、観測、close、復旧監査起動を提供する実行環境。
- **worker実行単位**：Planner、Implementer、Reviewer、Documenter等の論理責務を担当する実行主体。
- **handoff event**：工程完了、停止、Owner判断待ち、または結果資料更新を次の処理へ渡す再実行安全なイベント。記録項目、状態遷移、claim、確定点は`rules/handoff-event-contract.md`を正本とする。
- **復旧監査**：handoff eventの欠落、処理中イベントの残留、またはCoordinator停止を検出して安全に再開する低頻度の照合。通常の工程遷移を待機させる主経路にしてはならない。

## 実行バックエンドの能力契約

実行バックエンドは、利用可能な範囲で次の能力を提供する。

```text
接続       : 指定された論理責務を開始する
再開       : 同一taskの実行単位を再開する
観測       : 実行単位の状態または未確認範囲を返す
完了証跡   : 結果資料と完了・close相当の根拠を返す
通知       : handoff eventをCoordinatorへ渡す
監査       : 未処理イベントだけを照合する
```

能力の観測値を取得できない場合は`未確認`として取得範囲と代替証跡を記録する。結果資料、承認、対象task、実行環境境界、または代替証跡間の既知の矛盾がない限り、観測不能だけで通常工程を停止しない。

## イベント駆動の工程遷移

通常の工程遷移は、worker実行単位が結果資料を確定した直後にhandoff eventを発行して行う。Workflow Coordinatorは未処理イベントを一件ずつ照合し、承認済み範囲内で入力ゲートを満たす場合は追加の開始指示を待たず次工程を開始する。ただしReviewerの`受入`または`条件付き受入`は自律サイクルの終点であり、Documenter開始にはReviewer受入結果に対するOwnerの明示承認を別入力として必要とする。

通常経路の実現に、AIツール外の常駐プログラム、独自の言語ランタイム、ポーリング用サービスを要求してはならない。選択した実行バックエンドが提供する親Coordinatorの継続実行、worker完了通知、または完了待機機構を使い、同じCoordinator実行内でeventを受領・claimして次工程へ進める。これらの能力をバックエンドが提供しない場合は、自律サイクルを有効化せず、手動接続または別バックエンドをOwnerへ提示する。

```text
worker完了
  → 結果資料の確定
  → handoff eventの発行
  → Coordinatorによる照合
  → 次工程開始 / Owner判断要求 / 停止
```

同一eventの重複処理、並行した次工程開始、承認代行、不可逆操作の自動確定は禁止する。台帳、イベントID、処理状態、結果、再開条件は`rules/handoff-event-contract.md`に従い、未確認や競合を推測で解消しない。

## 復旧監査の境界

定期監査その他の復旧起動機構は復旧監査としてだけ使用する。通常工程の遷移を待機させず、次の場合だけ未処理イベントを照合する。

- 完了証跡があるがhandoff eventが確認できない
- `processing`状態のイベントが残留している
- Coordinatorまたは実行バックエンドの停止後に再開する

復旧監査は、停止、承認、close、削除、作成を代行しない。矛盾、結果資料欠落、承認不足、対象境界不一致、または復旧不能を検出した場合だけ、停止理由と再開条件を記録してOwner判断を求める。

## 実行バックエンドの選択

共通rulesは実行バックエンドを既定値として固定しない。対象taskの明示指定、または対象作業ディレクトリ・リポジトリ・ブランチ・利用シーンに完全一致する`rules/local/`のローカルルールで、実行バックエンドを解決する。ローカルルールの適用条件、優先順位、欠落・競合時の停止は`rules/local-rules.md`に従う。

選択結果は`current-task.md`へ記録するが、完全一致するローカルルールで解決済みの場合、Ownerが計画承認時に同じバックエンドを改めて指定・確認する必要はない。明示指定とローカルルールが競合する、またはどちらでも解決できない場合は、自律サイクルを開始せずOwner判断を求める。

他の実行バックエンドへ移行する場合は、共通概念の意味、結果資料、Owner判断、停止条件を維持し、固有の操作・ID・通知方式だけを置き換える。必要能力が提供されない場合は、その不足、影響、代替可否、再開条件を例外記録へ残す。

## 代替バックエンドの導入

代替バックエンドを導入する前に、実行バックエンド名、Coordinator、worker実行単位の接続方法、handoff eventの通知方式、復旧監査の起動方式、結果資料の保存先をcurrent-taskと承認済み計画へ記録する。次の対応表がすべて埋まるまで、自律サイクルを有効化しない。

| 共通能力 | 代替バックエンドでの実現方法 | 証跡 | 利用不能時の扱い |
| --- | --- | --- | --- |
| 接続 |  |  | 停止または手動実行への切替 |
| 再開 |  |  | 停止または新しい実行単位への明示切替 |
| 完了証跡 |  |  | 結果資料と完了記録を照合 |
| handoff event通知 |  |  | 復旧監査で未処理イベントを検出 |
| 復旧監査 |  |  | Owner判断を求める |

人間による手動実行を使用する場合も、結果資料を確定しhandoff eventを発行する責任を持つ担当者を記録する。手動実行は、承認、結果資料、停止条件、Owner判断を省略する根拠にしてはならない。

## 導入完了条件

次のすべてを満たした場合にだけ、実行バックエンドの移植を有効化完了とする。

- 特定バックエンド固有のID、API、状態値が共通入力スキーマの必須項目になっていない
- 結果資料、handoff event、Owner判断、停止・再開条件を移行後も同じ意味で記録できる
- `rules/handoff-event-contract.md`の台帳、状態遷移、claim、確定点を移行後も満たせる
- 通常遷移がhandoff eventで開始され、定期監視を待機条件にしていない
- 復旧監査が未処理・残留イベントだけを扱い、通常の工程遷移を遅延させない
- 代替バックエンドの能力契約、証跡、利用不能時の扱いが承認済み計画で確認済みである
