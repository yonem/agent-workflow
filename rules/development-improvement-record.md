# 開発サイクル改善記録ルール

## 目的

`docs/development-improvement.md` を、複数プロジェクトで再利用できる開発サイクルの改善知識として管理する。個別タスクの詳細、実装ログ、具体的なパスは対象プロジェクトの `result/task-log.md` に記録する。

## 記録対象

- 複数プロジェクトへ再利用できる改善点
- 共通ルール、手順、判断基準、失敗パターン
- 継続的に効果を確認できる改善案

汎用化できない個別事例は、永続改善記録へ登録しない。必要な場合だけ対象プロジェクトのタスクログや固有ドキュメントへ記録する。

## ステータス

- `評価中`：汎用性、対応要否、適用範囲を確認している。新規登録、追加調査、Owner判断待ちを含む
- `対応完了`：評価と必要なルール・手順への反映が完了している
- `適用外`：評価の結果、現在の運用には適用しない


## ステータス遷移

```text
評価中 → 対応完了
   └→ 適用外
```

## 改善項目の記録形式

1改善項目を1ブロックで記録し、横長の表形式は使用しない。記録は `評価中` と `評価済み` のセクションに分け、`評価済み` に `対応完了` と `適用外` をまとめる。

```markdown
### IMP-XXX：<改善テーマ>

- 種別：
- 記録日：
- 更新日：
- 優先度：高 / 中 / 低
- ステータス：評価中 / 対応完了 / 適用外
- 課題：
- 対応案：
- 反映先：
- 適用範囲：
- 次回確認日：
- 見直し条件：
```

必須項目は、改善ID、種別、記録日、優先度、ステータス、改善テーマ、課題、対応案、適用範囲とする。該当しない任意項目は省略してよい。

## 更新ルール

- 既存の改善項目は削除せず、状態、対応案、反映先、次回確認日を更新する
- 新規項目には一意の `IMP-XXX` を付ける
- 汎用化できる内容へ抽象化し、製品名、プロジェクト名、リポジトリ名、パス、顧客情報を記録しない
- 事実と推測を分け、確認済みと未確認を混同しない
- 詳細な経緯、ログ、実装内容、タスク固有の判断は `result/task-log.md` へ分離する
- Documenterは記録後、変更した改善項目を親タスクへ報告する
