# コミットメッセージ規約

## 形式

```text
<prefix>: <What：何を変更したか>。<Why：なぜ変更したか>
```

コミットメッセージは、変更内容（What）と変更理由（Why）が伝わるようにする。

## Prefix

| Prefix | 用途 | 例 |
| --- | --- | --- |
| `add` | 小さなファイル・コードの追加 | サンプル、画像、補助ファイル |
| `change` | 小さな変更 | 文言、設定、サンプルの差し替え |
| `feat` | 利用者が使う機能・仕組みの追加 | 新しいテンプレート、導入機能 |
| `style` | 動作を変えない見た目・形式の変更 | Markdown整形、CSS |
| `refactor` | 動作を変えない構造改善 | ファイル分割、命名整理 |
| `fix` | 不具合の修正 | 誤ったリンク、検証漏れ |
| `remove` | ファイル・機能の削除 | 不要なテンプレートの削除 |
| `test` | テスト関連 | テスト追加、テスト修正 |
| `chore` | ビルド、依存、補助ツール、CI | GitHub Actions、設定更新 |
| `docs` | 文書のみの変更 | README、手順書、規約 |

## 運用ルール

- 1コミット1目的とする
- Prefixは変更の主目的で決める
- `feat`は利用者が得る新しい機能・仕組みの追加に使う
- 変更内容だけでなく、可能な範囲で理由も書く
- 無関係な変更を同じコミットへ混在させない
- 秘密情報や個人情報をコミットしない
- AIが作成した場合も、人間が内容とPrefixを確認する
- コミットメッセージだけで要件や設計判断を代替しない

## 例

```text
feat: 初回PJ向けの導入手順を追加。参画直後の作業開始条件を明確にするため
fix: 検証結果の判定欄を修正。合格基準を記録できなかったため
docs: サブエージェントのリレー方式を整理。役割間の引き継ぎ方法を統一するため
```

## Codexへの依頼例

```text
変更内容を確認し、コミットメッセージ案を提示してください。

ルール：
- 1コミット1目的
- Prefixを付ける
- WhatとWhyを短く含める
- 未追跡ファイル、秘密情報、計画外変更を確認する
- 人間の確認を受けるまでコミットを作成しない

形式：
<prefix>: <何を変更したか>。<なぜ変更したか>
```

## コミット前チェック

- [ ] 変更内容とPrefixが一致している
- [ ] 1つの目的にまとまっている
- [ ] Whatが明確である
- [ ] Whyが必要な場合に記載されている
- [ ] 計画外の変更が混ざっていない
- [ ] 秘密情報・個人情報が含まれていない
